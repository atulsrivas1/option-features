Author: Architect, 2026-10-29. Status: DRAFT, independently reviewed twice (PR 75); every question Q1-Q18 is RULED (interim, pending design ratification where the design is silent). Gate item of docs/M1_CLOSE.md section 5 step 1 and PO release plan V3 section 3. Format follows the M1 matrix (R28A_B_CAPABILITY_MATRIX). Companion docs: M2_GATE_BUDGETS.md, M2_FIXTURE_REQUIREMENTS.md, M2_IO_CONTRACT.md.

Sources of truth: design text flow.md (F rows, sections 2.2, 2.3, 2.7, 2.8, 14), option-contracts.md (gates), audits/workers-vs-conditions.md (read as audit only), DESIGN_SESSION_REQUESTS (request 5 zero baseline, request 9 baseline statistic), PO_PARITY_RECONCILIATION (F row status), docs/FLOW_NAMING_MAP.md (repository ids, reason vocabulary), P1 modules `windows`, `shares`, `quotes`.

Owner main goal: performance. Every M2 output is a pure, exact-arithmetic, batched function; one pass over the trade stream feeds all families; history is read through sorted views; so the runner (tools/m1_runner, opt-in, default single-process) can use cores and caches without changing a result byte.

## 1. Scope, legend, assumptions
- In M2 (V3): F1, F2 (percentile rank, history store), F4 (count and threshold), F7, F10 and F20 (both baseline statistics, Q4 RULED), F17 (fixed 5-minute window), F18, F19, F12; then the re-audit of every F row (section 7).
- Data per the project data-sources assumption: mock/synthetic quote and trade streams, daily totals and calendars, generated by the Tester. A vendor-style feed, FMP and public sources are described below only so the shape is ready; every source column "applies at RQ". No adapter, vendor schema or network work in M2.
- Client = could run on a bring-your-own-key desktop host if a provider supplies the data; Server = needs the trade stream or history a single key will not supply; Either = pure library kernel (D4). Availability: FULL, DEGRADED, UNAVAILABLE (reason from the closed set, section 4). No silent fallback between sources; values from different sources are never merged.
- Exact arithmetic: premium = price x size x multiplier in integer ticks / Fraction; shares, ratios and ranks are Fractions; no float in M2 (nothing needs IV). Eligible print = standard print as in `windows.window_premium` (multiplier 100; other multipliers excluded and counted as excluded_nonstandard_count; excluded-condition prints excluded and counted).
- Windows are closed at both ends [T-W, T], T = evaluation time (PO-P1-02, same as F3). Trailing windows never look ahead of T.

## 4. Closed reason set and status
Statuses: available, unavailable (with reason), invalid_input (structural; carries an error code). The M2 reason set is closed; a new reason needs a PO ruling:
| Reason | Meaning |
|---|---|
| insufficient_history | fewer than the minimum complete prior sessions, including none stored (design shows "new", no value) |
| session_not_complete | end-of-day form requested before the session is sealed complete |
| zero_denominator | ratio or share denominator is 0 |
| insufficient_window | F1, F2, F10 and F12: the window or grid point lies before session open + W (observed time since open is under W; 900 s for F1); windows are not clipped for these outputs, the result is unavailable (cannot over-fire); the history n of a rank or median excludes, per session, the grid points before open + W |
Quote reasons (`no_quote` and the rest) do not appear: M2 needs no quotes. No new synonyms (Q6 RULED): mapping to the existing vocabulary: median or mean equal to 0 -> zero_denominator (the ratio denominator is the statistic); nothing stored or fewer sessions -> insufficient_history (repository empty_baseline and insufficient_history); zero_mad is not used (no MAD in M2). Structural error codes (invalid_input): unordered input, negative size or price, bad multiplier, duplicate session, non-monotone grid, session not in calendar, window not in the allowed set, delayed_feed_tag (F1, F12, intraday F2 and intraday F10 under a delayed feed). Gate order: invalid_input, insufficient_history, session_not_complete, insufficient_window, zero_denominator. Fixtures assert the reason, not only the status.

## 5. History store needs (PROPOSED design, no code)
- Keyed by (series id, metric, session). Series are names (F2, F12, F19, F20 and name-level F10) and, only if the PO rules contract-level F10 (Q5), contracts.
- Per record: metric values on the 60 s grid (390 for a 6.5 h session), the session total, a complete flag, a content hash. Sorted copies are built once when a session is sealed and reused by every read (cache rules in the budgets doc).
- Append-only per series in session order; retention K sessions (default 20) in a ring. Five stored metrics per series (premium, contracts, prints, put volume, call volume), array-backed, each with a sorted copy and one merged sorted array for the median. Contract-level series are sparse (nonzero grid points plus a zero count) and created lazily only for contracts with prints (about 64 KB at the median print count); name-level series are dense (about 0.9 MB, 5 names). Store budget 512 MB, hard 1 GB per worker (PO ruling); contract-level series are capped by that budget and the number held is reported.
- A read returns an immutable, hashable view as of a session; a unit reads only sessions strictly before its own session (no look-ahead).
- Serialization is deterministic (canonical order, LF text). The store is derived data: only its content hash goes in the run log, never into a result.
- Parallelism: the build phase is ordered per underlying (sessions in order) and parallel across underlyings; the compute phase over units reads immutable views.

## 6. Byte impact

No R25, R26, P1 or M1 result byte changes; `variants1` legacy `baseline`, `directional` and `premium` keep their bytes and the sentinel policy. PROPOSED: no version bump for M2 itself; wire exposure of the P1, M1 and M2 modules is the candidate16 item. A bump follows only if the PO rules a change to a shipped output (for example request 5 option A applied to variants1), as a candidate bump with fixtures.
