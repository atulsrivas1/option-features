Status: architect draft, 2026-10-27 (story S2), proposed for independent review. Docs only: no code, fixture, freeze or implementation authority follows. It supplements the existing PUBLIC_SAFE_*_CLARIFICATION1 documents and changes none of them.

Evidence base and its limit. Rulings use only (a) the public contract text in docs/r26 (FLOW_CONTRACT.md is the superseded flow candidate; the variants boundary text and its "section 13" are private and were not available here, so statements about section 13 are quoted from DECISIONS.md and not re-verified), (b) the shipped code at tag r26-variants1-prerelease (option-features, option-feature-io, option-feature-workers, the last two read only), and (c) the existing clarification documents and DECISIONS.md. ## 1. field_set missing/extra field pointer

- Current behaviour: the library (schema.py `_check_record`, stage 3) reports `field_set` at the offending field path (`/rec/field`) for both a missing and an extra field. The I/O codec re-points both to the parent record (io codec.py `_shape`, `exc.path.rsplit("/",1)[0]`). The 1,502 frozen W3-field rows expect the parent pointer (DECISIONS 2026-10-23). A union object without `kind` is `field_set` at `/rec/kind` in the library, re-pointed to the union object by the same codec step. Duplicate JSON keys are `field_set` at stage 2 at the first duplicate key (io codec.py); a wrong envelope key set is `field_set` at `/envelope`, stage 3.
- Proposed ruling (**proposed, needs independent review**): for a missing or extra member of a closed record (including a union object missing `kind`), `field_set` at stage 3 points to the record that fails the check (the parent), not the member. Within a record, report the first missing field in declaration order; if none is missing, the first extra member in supplied order. Duplicate-key pointer unchanged. This matches the frozen fixtures and the codec; the library's direct (non-codec) child pointer should be re-aligned in a follow-up code story.
- Rationale: one normative pointer shape for every entry path; frozen rows already encode it; the contract names only code and stage.
- Fixtures needed: missing first/last field; extra field before/after known fields; missing plus extra in one record (missing wins); nested record in an array at index > 0; union without `kind`; envelope-level missing/extra key; duplicate key unchanged. The 1,502 W3-field rows cover most; add missing-plus-extra and extra-in-supplied-order.
- Erratum (2026-10-27): "the 1,502 frozen W3-field rows" in the lines above is inaccurate. 751 of them are field_set (missing member) and 751 are type_mismatch; 782 stage 3 field_set rows in all (including extra-member and array-element union rows) assert the parent pointer. See PUBLIC_SAFE_FIELD_SET_POINTER_CLARIFICATION1.md, which supersedes this section.

## 2. Rolling envelope member ids and the four undetermined rolling cases

- Current behaviour (lib flow.py `directional_b64`, `rolling_window`): `DirectionalObject.premiums` and `Evidence.eligibility` carry the full-session raw population; `Evidence.member_ids`/`member_revision_ids` are the known-positive roots inside window M; roots outside M are added to `excluded_ids` with known-zero and capture exclusions. When capture is incomplete, any raw premium is unresolved, or there is no positive root, no window is certified: `rolling_window` returns the endpoint control's event domain as interval and an empty member list, and metrics are unavailable (`incomplete_capture` first, then `premium_unavailable`). r is the maximum event_ns over positives; the interval is `(max(0, r - horizon_ns), r]`.
- Proposed ruling:
  1. Certified window: `member_ids`/`member_revision_ids` are the known-positive members inside M, in (event_ns, admission_ordinal) order; count metrics describe them. Settled by the rolling clarification and code.
  2. `excluded_ids` holds known-zero roots, capture exclusions and every full-session root outside M. Settled by clarification and code.
  3. No-r envelope: `member_ids` and `member_revision_ids` are empty and `member_interval` is the endpoint control's event domain; the raw population remains in `premiums`/witnesses. Settled by code; the clarification says only "the already defined full-session envelope".
  4. Tie at r: both positives are members; order by admission_ordinal after event_ns. Code orders via `order_members` and selects r by event_ns only. **Proposed, needs independent review** that the order is `(event_ns, admission_ordinal)`.
- The four undetermined rolling cases (private names not in this repo, so identified by the clarification's own list): (a) excluded positive lower endpoint: the lower bound is exclusive, so a positive exactly at `r - horizon_ns` is not a member and is listed in `excluded_ids`; (b) older positive strictly below the bound: excluded, does not move r; (c) known-zero row inside the window: not a member, in `excluded_ids`; (d) two positives tied at r: both members, r is that event_ns. These follow from the strict-interval formulas in code but are **proposed, needs independent review** because the freeze review left them undetermined. Unresolved premium anywhere, including at or below the lower bound, yields the no-r envelope (clarification and code).
- Fixtures needed: one full-input case per item, plus later known-zero endpoint witness, unresolved membership with known r, and complete-empty envelope; each asserts member_ids, member_revision_ids, excluded_ids, member_interval and window-versus-full-session counts.

## 3. DailyCore excluded-candidate Results and Scope pointers

- Current behaviour (lib baseline.py `slot_info`, `daily_reduction`): every observation in a slot's `observation_ids` is derived; those matching right/DTE/moneyness are `selected`, others `excluded`. Only selected observations enter `DailyCore.observation_ids`/`contract_ids` and folds. `input_record_sha256s` includes the Scope of the op, of the slot and of every observation in the slot (selected and excluded), as a set; Evidence dependencies add the same Scopes. Excluded candidates produce no Result row and no diagnostic. A candidate whose bucket derivation fails marks the whole slot missing before inclusion is decided.
- Proposed ruling (**proposed, needs independent review**): (1) excluded candidates produce no Result rows and no DailyCore entries; they appear only as proof inputs (current behaviour). (2) The DailyCore Scope input set is the existing DailyCore Scope clarification applied to every observation listed in the slot whose status was determined; code determines status for every listed observation, so this is all listed observations. (3) For a slot missing before determination there is no DailyCore; slot-level evidence still lists the Scopes of all listed observations (code behaviour, retained). (4) Scope incompatibility remains `identity_mismatch` at stage 6; pointers are those raised in lib admission_act.py, indexes being actual array indexes with the first offender in declaration then index order; this document does not change those strings. If the private fixtures assert a Result row for an excluded candidate they contradict this ruling and need correction.
- Fixtures needed: multi-day, multi-contract slot with one excluded-by-right, one excluded-by-bucket and one missing-reference candidate; identical Scope on slot and observation (counted once); different Scope on an excluded candidate only (still in the hash set); unrelated registry Scope absent; compatibility error pointer with index > 0.

## 4. Restore i > 0: cursor regression, no stream drop, Request immutability

- Current behaviour (workers checkpoint.py `validate_restore`): after CP0-CP2 and shape/scalar checks, CP3 does: producer-admission prefix mismatch `checkpoint_cut_mismatch` at `/checkpoint/producer_admission`; `knowledge_K_ns` regression `checkpoint_cut_mismatch` at `/request/knowledge_K_ns`; cursor regression in current index order at `/request/cut_cursors/{i}/position` (equal allowed; only streams present in both compared); then immutable merge: `identity_conflict` at `/snapshot/{collection}/{i}` and suffix-internal duplicate identities at `/snapshot/{collection}/{i}/{key}`. Not implemented: a check that a retained stream is still present, any comparison of other Request fields with the prior Request, and stage-7 temporal checks on the current Request and suffix before the regression checks.
- Ruling (strict rejection is coordinator-ruled; the rest is **proposed, needs independent review** where the contract is silent):
  1. Cursor regression: `checkpoint_cut_mismatch` at `/request/cut_cursors/{i}/position`, i the actual index in the current Request's canonical list; equal position is not a regression. Existing clarification and code.
  2. No stream drop (reading (a), decided): a retained stream absent from the current Request's cut cursors is the same rule as the restore clarification's "missing-stream" error, not a new rule. It therefore keeps that rule's existing code and pointer and its position in CP3 (with request shape, scalar and admission errors, before the temporal rules and the cursor-regression scan). This document defines no new code, pointer or position for it. Caveat: the existing missing-stream code and pointer are defined in the private boundary text; neither this repo nor the shipped restore code (`validate_restore`) implements or states them, so the shipped code silently accepts a dropped stream. This is a code gap to close against that text, not a rule invented here. Because the check is a pure presence test, its position relative to the regression scan is fixed by the clarification, not chosen here.
  3. Request immutability: **restrictive guess, not contract-derived; do not use in fixtures until the contract is checked.** The guess is that every current Request field other than `knowledge_K_ns`, `cut_cursors` and the `emit` window must equal the prior Request, with `checkpoint_cut_mismatch` at `/request/{field}` for the first differing field in Request declaration order.
  4. CP3 order as the existing clarification states it: current Request shape, scalar, admission and missing-stream errors under their existing rules; then the existing temporal rules (A>K `temporal_cut` at `/request/knowledge_K_ns`); then cut-cursor regression in index order; then suffix stamped position and known-at; then immutable merge `identity_conflict`. The only placements this document proposes (**proposed, needs independent review**) are: the `knowledge_K_ns` regression check sits after the temporal rules and before cursor regression (the clarification does not mention it; code has it first), and the Request-immutability guess, if ever adopted, sits after cursor regression.
- Code differences to log: code raises merge `identity_conflict` with stage number 3 and suffix duplicates with stage 5; the worker surfaces typed code and path, so stage numbers there are not observable.
- Fixtures needed: regression at index 0 and at index 2 (first reported); equal position accepted; two streams regress (lowest index reported); retained stream dropped (only once the missing-stream code/pointer is confirmed); cursor list reordered with the same set; K regression alone; K regression plus cursor regression (K first); cursor regression plus identity_conflict (regression first).

## 5. PR 12 lane control and overflow placement

- Current behaviour (lib groups.py): lanes are keyed by `partition_key` (contract, right, strike, expiry, multiplier, side). A group is complete only if the capture control covers `[a_ns, a_ns + w)` and some complete `lane_prefix` control from `op.lane_prefix_ids` has an event_domain containing `[partition_start_ns, a_ns]` (closed both ends); the control is not bound to a contract or partition. Group reason: `incomplete_capture` if incomplete, else `premium_unavailable` if any member premium is unavailable, else `premium_overflow` if the summed premium overflows (`_group`). Member overflow (lib premium.py) gives the member `premium_overflow`, which becomes `premium_unavailable` at the group.
- Proposed ruling (**proposed, needs independent review**): (1) lane control placement: coverage is evaluated per PR 12 partition; a complete `lane_prefix` control covers a partition when its event_domain contains the partition's closed interval from `scope.partition_start_ns` to the anchor ns. Shipped behaviour (one control may cover several partitions, no per-partition binding) is retained because no Control field carries a partition binding; adding one is a schema change outside S2. (2) Overflow placement: member overflow gives group reason `premium_unavailable` (PR 12 amendment, matches code), the member's own `premium_overflow` stays in its PremiumCore Metrics/Diagnostics, and a summed overflow is `premium_overflow` at the group Metric. Receipt priority stays `incomplete_capture`, then `premium_overflow`, then `premium_unavailable`.
- Fixtures needed: two partitions under one contract_id, one covered by the lane control and one not; control covering only part of the interval; member overflow, sum overflow and both; incomplete capture plus overflowing member (incomplete_capture wins); receipt reason aggregation across mixed groups.

## 6. A>K temporal_cut order

- Current behaviour (lib admission.py `stage7`): temporal checks are stage 7: control visibility `temporal_cut` at op control pointers, then for `span_at_anchor` and `premium` ops a selected revision's signing A greater than K is `temporal_cut` at `/request/knowledge_K_ns`. In restore (workers checkpoint.py) these checks run on the retained history during CP0-CP1 and are not re-run for the current Request and suffix before the regression checks.
- Proposed ruling (**proposed, needs independent review**; it matches the restore clarification: "then the existing temporal rules ... then cut-cursor regression"): in CP3 run the stage-7 temporal admission over the current Request and suffix before the `knowledge_K_ns` regression and cursor regression checks. An A>K root yields `temporal_cut` at `/request/knowledge_K_ns` even when K also regressed. K regression and A>K share the pointer with different codes (`checkpoint_cut_mismatch` versus `temporal_cut`); temporal wins. Within the temporal step keep the stage-7 order and pointers of lib admission.py and admission_act.py.
- Fixtures needed: A>K with K regressing (temporal_cut); A>K with cursor regression (temporal first); K regression only; K regression with A<=K (checkpoint_cut_mismatch); op-control temporal_cut and an A>K root in the same Request (stage-7 order).

## 7. observed_series incomplete-slot behaviour

- Current behaviour (lib baseline.py `baseline`): `coverage` (`observed_series` or `certified_expected_slots`) is echoed into the BaselineValue and not otherwise used. A slot that cannot form a daily reduction (missing or future reference, incomplete control, expected-contract mismatch, missing activity certificate, incomplete premium core) goes to `missing_slot_ids`; the gap reason is the first in `REASON_ORDER` (`missing_reference`, `future_reference`, `incomplete_baseline`) and makes every statistic unavailable with that reason; present samples are still listed. `slot_ids` is explicit in the op.
- Proposed ruling (**proposed, needs independent review**; the contract is silent on any behavioural difference between the two values): both coverage values evaluate identically; an incomplete or missing selected slot makes the statistics unavailable with the reason order above, because the op names its slots and silently skipping one would drop a selected slot. `coverage` is descriptive. If the intent is that `observed_series` uses whatever slots are present, that is a new amendment with its own fixtures.
- Fixtures needed: one incomplete slot in each mode; incomplete slot at index > 0; two different missing reasons (order); all slots complete in both modes (identical statistics); zero slots (`empty_baseline`).

## 8. Unknown-tag stage (3 vs 4)

- Current behaviour: for a tagged union an unknown `kind` is `invalid_scalar` at stage 3 at the `kind` member (schema.py `_check_one`); a non-string `kind` is `type_mismatch` at stage 3; a missing `kind` is `field_set` at stage 3. The nine W3-union `*-unknown-tag` rows expect stage 4 and are excluded as fixture defects (DECISIONS 2026-10-23).
- Ruling: stage 3, as the coordinator states contract section 13 says and as shipped (choosing the record shape needs the tag, so the tag is a shape check). Code `invalid_scalar`, stage 3, pointer at the `kind` member. Other enumeration members stay stage 4.
- Fixtures needed: the nine rows regenerated at stage 3 with the `kind` pointer; unknown tag in an array at index > 0; unknown tag plus an earlier stage-4 defect (stage 3 wins); unknown tag nested in a union.

## 9. N4 schema notes

- bp versus bits (schema.py token table, `_check_scalar`): `bits` is any finite binary64 pattern including negative and negative zero; `bp` is finite and strictly positive; `bn` is finite and nonnegative. `RawBinary64Price` and `Binary64Multiplier` are `bp`; `QuoteBinary64Price` and `B64Number` are `bits`. Ruling (settled by code): fixtures must not put zero or negative bits in a `bp` field (stage 4 `invalid_scalar`); they may in `bits` fields. Open: `RawBinary64Price` is `bp`, so an exactly zero binary64 execution price is rejected at stage 4 although the integer price form permits zero; the contract text does not say which is intended. **Proposed, needs independent review**: keep `bp` as shipped and record it; relaxing to `bn` would be an amendment.
- monetary_basis reverse direction (schema.py `_rule_metric`): the rule is two-way. `unit == currency_ticks` requires non-null `monetary_basis`, and non-null `monetary_basis` requires `unit == currency_ticks`; either violation is a stage 4 record rule at the Metric's `monetary_basis` pointer. Ruling (settled by code): fixtures need the reverse case (basis present with a non-currency_ticks unit) as well as the forward case.
- Fixtures needed: zero, negative, negative-zero, NaN and infinity bits in `bp`, `bn` and `bits` fields; basis present with unit contracts; basis absent with unit currency_ticks.

## 10. Worker codes cohort_unverified and execution_failed

- Current behaviour (workers execute.py, run.py, storage.py): `cohort_unverified` is raised before evaluation for: no verified cohort; cohort artifact inventory not exactly the five pinned artifacts (the pure-library subset is rejected); producer-admission hash differing from the config or request hash; a qualified input whose receipt hash is not in the config receipt set; and a false verification flag inside compute. `execution_failed` is raised by the sink wrapper when publish raises an unclassified exception and verified readback finds nothing stored, and by storage `publish` when the publication schema version or cohort digest is inconsistent. Typed storage, publication-conflict and validation errors pass through unchanged. `cohort_changed` and `resource_*` are separate codes.
- Proposed ruling (**proposed, needs independent review**; FLOW_CONTRACT section 9 lists the codes without triggers): `cohort_unverified` means the supplied cohort or producer admission cannot be proven to be the exact installed pipeline for this run (missing, wrong inventory, hash or receipt mismatch); it is always raised before evaluator or sink invocation and carries no cause fields. `execution_failed` means a failure after admission that is not a typed validation, resource, conflict, integrity or schema error; the original exception is chained, no structured cause is added, and it never follows a partial publication (readback finds nothing or a verified match). Precedence: unsupported mode/resources, then `cohort_unverified`, then `input_invalid`, then execution outcomes.
- Fixtures needed: inventory missing one artifact; inventory with an extra artifact; admission hash mismatch; unknown receipt hash; None cohort; sink raising after storing the identical publication (recovered, no error); sink raising with nothing stored (`execution_failed`); sink raising after storing a different publication (`publication_conflict`); publication with wrong cohort digest at storage.
