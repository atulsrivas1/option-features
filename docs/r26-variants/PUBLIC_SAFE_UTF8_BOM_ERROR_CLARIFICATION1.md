# Strict UTF8 BOM error precedence

2026-10-21. Coordinator proposal for fresh independent review, refining the existing no-BOM canonical transport requirement. No record, formula, wire encoding, error token or stage is added. All earlier sealed inputs remain unchanged; no freeze or implementation authority follows.

A leading UTF8 BOM, bytes `EF BB BF`, is valid UTF8 but is not admitted JSON syntax in this strict wire profile. The decoder does not strip or ignore it. Report `VariantValidationError('invalid_json','/envelope')` at stage2, before closed-record field/scalar/reference/coherence/digest checks. The decoder checks stage1 (wire size and allocation limits, UTF8 validity, token depth) first, so an earlier stage1 defect keeps its stage1 code. Otherwise a BOM at byte offset 0 is the first syntax error and is reported as `invalid_json` at `/envelope` before duplicate-key `field_set` or any stage3+ check. A BOM is recognised only at offset 0; any other U+FEFF outside a JSON string is ordinary invalid syntax. For BOM-prefixed input this supersedes the stage9 `noncanonical` reading of the byte-for-byte rule. Malformed UTF8 remains `invalid_utf8` at stage1 even after a BOM. Ordinary syntactically valid JSON with noncanonical whitespace, member order or spelling retains the existing stage9 canonical-byte check and its existing precedence before digest comparison.

This concerns only a leading transport BOM outside the JSON text. It does not reinterpret a character inside a JSON string, relax the existing scalar/NFC rules, admit another character encoding or normalize any bytes. Independent raw-byte and compound-error fixtures (BOM with bad UTF8, BOM with excessive depth, BOM with a duplicate key, double BOM) plus independent review remain required before the final literal/implementation freeze.
