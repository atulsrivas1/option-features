# M1 process-pool runner (opt-in, default single-process)

Label: mock-data qualification only: passed on independently authored synthetic fixtures and synthetic workloads, Windows x64, CPython 3.12. All numbers are "synthetic workload, relative engineering budget". Developer evidence only; the independent Tester authors and re-runs the determinism, kill and scaling tests and the platform replays.

The runner is opt-in, default single-process. It is a separate optional tool (`tools/m1_runner/`, not shipped in the libraries, no change to the record schema or to any result byte). The libraries stay single-threaded and pure (D4 amended). It is never enabled by default anywhere: `--workers` defaults to 1, which runs in this process and is the reference path. Every other worker count must give identical result bytes.

## What it computes
Units are underlying x session x cutoff (unit key `SYN1/03/045`). Since M2-G0 one unit computes the FULL output set on one size-M chain (2,000 contracts) at one cutoff: per-contract IV, ATM IV for every expiry and 30-day IV (`option_features.chainiv`), OC5 and OC6 for every contract (`imbalance`, `spreadwin`), and the P1 outputs the library ships, over the unit's synthetic quote and trade streams: spread/locked gate and quote-count coverage per contract at the cutoff (`quotes.spread_reason`, `quote_spread`, `windows.QuoteUpdateIndex`), touch-policy signing of every print and spread gate of every quote in one pass (`quotes.classify_stream`, the quote stream up to the cutoff plus the prints, about 340,000 records at cutoff 39), window_end premium windows per contract for 5 and 30 minutes ending at the cutoff (`windows.WindowIndex`) and single-reference F5/F6 shares for the chain and per expiry (`shares.single_reference_shares`). The driver adds no calculation; `tools/m1_runner/workload.py` only builds the synthetic inputs from `qualification/synthetic/perf/gen_perf_workloads.py` (read only) and calls the pure modules. Units share no state. The whole workload is 5 underlyings x 5 sessions x 78 cutoffs = 1,950 units. Shape `T` (40 contracts) exists for CI tests.

Frozen trade stream (`Spec.prints`, default 20 per contract = 40,000 prints per size-M unit): 70 percent of prints fall within 4 s after a quote update at or before the cutoff, 30 percent are uniform in the trailing hour; price is 35 percent at the ask, 35 at the bid, 15 inside, 7 one tick beyond the touch, 8 near the mid of the quote in force; size 1 to 100; 2 percent carry a non-standard multiplier. It is a pure function of the unit and does not depend on contract order. Because the generator's quote stream is sparse per contract (median 50 updates per session), most quotes are stale at the cutoff and the P1 spread gate reports `stale_quote` for them; that is the workload, not a library fault.

The unit also runs `quotes.sign_aggregate` per contract (premium by side, call-ask plus put-bid and put-ask plus call-bid premiums, shares, status) over the contract's prints against the quote in force, next to `classify_stream`; the three premium totals of `classify_stream` equal the sum of the per-contract aggregates (tested). Measured M2-G0 workload facts (Developer, PR 77): the trade stream is a developer-authored construct with a uniform 20 prints per contract (40,000 per size-M unit); the median 20 / p99 1,000 tail of the section 2 proposal is NOT modelled, and the windowing cost is mostly insensitive to it (one index build and two bisect queries per contract). Beside the IV figure: of 2,000 contracts 985 solve (261 invalid_quote, 744 american_itm, 10 price_out_of_bounds), so the IV time is the cost of 985 certified solves plus the gating of the rest.

Input synthesis (quote history, chain rows, prints, conversion into library input shapes: `workload.build_inputs`) is separate from the compute (`workload.compute_from_inputs`); `compute_unit` calls both. Optional log-only timing (`timing` dict, per-family seconds; the runner log carries it per chunk) never enters result bytes.

## Usage
```
python tools/m1_runner/cli.py --shape M --workers 48 --out OUTDIR --emit full --log run.jsonl
python tools/m1_runner/cli.py --shape T --underlyings SYN1,SYN2 --sessions 1-2 --cutoffs 0-2     # reference path, 1 worker
```
Options: `--workers N` (default 1), `--batch-size`, `--order natural|reversed|shuffle:K` and `--contract-order` (test levers: results must not depend on them), `--emit digest|full`, `--out DIR`, `--log FILE`, `--b9-peak-bytes`, `--aggregate-hard-bytes`, `--cores` (physical), `--ram-bytes`, `--timeout-s`, `--count-arb`, `--fault`. The API is `m1_runner.Runner(workers=N)` as a context manager and `runner.run(spec, batch_size, order, emit, out_dir)`. The interpreter that starts the run is the interpreter of every worker; it must be the one that has python-flint.

Workers are persistent processes started once (Windows: `spawn`) and fed chunks of one underlying x session and consecutive cutoffs, which amortises IPC and lets a worker keep the quote history it built for its session (derived data, dropped between runs; results never depend on it, tested). Dispatch is dynamic and sticky (an idle worker prefers a chunk it can serve from its cache); this is a scheduling heuristic only.

## Caps
`cap = min(physical cores, floor(aggregate limit / B9 value))`, at least 1 (PO ruling). The B9 value in the cap is the 2 GB budget (`--b9-peak-bytes`), not the measured peak; the aggregate worker RSS limit is configurable (`--aggregate-hard-bytes`) and defaults to 50 percent of host RAM, so the default cap is `min(physical cores, floor(0.5 x host RAM / 2 GB))`. Logical cores are only reported. Requested workers above the cap are clamped and the clamp (requested, used, cap) is reported in the run log; it is not an error. Cores, RAM and the limits are injectable for tests. The aggregate limit is enforced on measured peak working sets on the pool path only (workers 2 or more; the in-process reference reports its own peak but is not limited): workers report their peak after each chunk and the run fails with `MemoryLimitError` above the limit. The B9 gate itself stays 2 GB budget and 4 GB hard per process; the measured per-worker peak (about 0.5 GB on the B7 workload) is reported as a fact.

## Failure semantics: no partial output
A worker crash (`WorkerCrashedError`, names the worker, pid, exit code and the chunk), a chunk timeout (`WorkerTimeoutError`), a missing unit (`MissingUnitError`, names the unit keys), a duplicate or unexpected unit, a worker exception (`WorkerFailedError`), a worker whose interpreter, python-flint version, platform or library path differs from the parent (`InterpreterMismatchError`, checked at start) or the aggregate RSS limit (`MemoryLimitError`) fails the whole run: the pool is terminated, the command exits 2 with the named error on stderr, and NO output file is written, no digest, no temp file. Outputs (`digests.json`, and `results.jsonl` for `--emit full`) are written only after every unit is merged, to temp names and then renamed. `--fault kill_worker:W:N`, `drop_unit:KEY` and `hang_worker:W` exist for tests.

## Process hygiene
Benchmarks and cleanup terminate only the process ids they started, never by name or command-line pattern. Outputs of a previous run in `--out` (`digests.json`, `results.jsonl`, `.*.tmp`) are removed when a run starts and again before writing, so a failed run never leaves old outputs. When workers are clamped the CLI prints `clamp: requested N used M cap C` to stderr (stdout never carries the worker count).

## M2 families (opt-in, default single-process; additive, M1 behaviour and defaults unchanged)
`--family m1` (default) is the M1 unit above. `--family prints|window|volume|concentration|grid|baseline|history|episodes|store|m2|all` selects an M2 unit (docs/m2/M2_IO_CONTRACT.md outputs): unit key `SYN1/21/045` is underlying / session / cutoff index, evaluated sessions 21 to 25 (the history sessions 1 to 25 live in the store). One `m2` unit, on the unit prints of one underlying and session (`gen_m2_workloads.py`, read only), computes F1, F4, F17, F7, F18, F12 from one print tape at the cutoff T = open + 300 s x (index + 1), and for every series S0000.. (series s is contract id s; `--series-count`, default 2,000) F2a to F2d and F10 from the history store (fused `flow_pack_many`; `--path single` uses the one-at-a-time calls and must give equal bytes), plus F2b end-of-day and F20 at the last cutoff. `all` adds the M1 unit of the same underlying and cutoff (session k - 20). Other options: `--history-sessions 20|25` (K of the baseline reads; 25 reads as insufficient_history by construction), `--cache warm|cold|off` (tape cache; equal bytes), `--mutation JSON` (kinds print, contract, history, calendar, param; a kind that does not apply is an error), `--unit-prints N` (test lever, default the frozen 40,000), `--store-bytes-hard`. Added faults: `duplicate_unit:KEY`, `truncate_store:BYTES`, `corrupt_store:OFFSET` (pool only).

History store transfer. The parent generates the store once per run (series x 25 sessions x 5 metrics, window 300 s, ring 25) and, for 2 or more workers, writes it as a binary M2BIN snapshot under a new file name per generation (`history-g<N>-<content hash>.m2bin`, a mapped file cannot be replaced on Windows; the files live in a temporary directory the Runner creates and removes). Each worker maps it read-only (`HistoryStore.attach_binary`: shared file-backed pages, magic, length and SHA-256 verified), compares `content_hash()` with the generation hash after the attach (a mismatch, a truncated or a damaged file fails the run with `StoreAttachError` naming the worker and the library code, e.g. `snapshot_hash_mismatch`, and no output file), runs `gc.freeze()` and acks. The in-process reference path uses the built store directly; results never depend on the transfer form (tested). The run log carries, per worker, the attach seconds, private bytes (the working-set growth of the attach, the store memory per worker) and the shared mapped bytes apart. Store memory per worker is enforced: the hard limit `--store-bytes-hard` (1 GB) fails the run with `MemoryLimitError`; the 512 MB budget is reported (`over_budget_workers`).

## perf_sut (M2 JSON binding, contract version 3)
`python tools/m1_runner/perf_sut.py --request REQ.json --response RESP.json` implements the JSON binding of `qualification/synthetic/m2/perf/M2_PERF_RUNNER_CONTRACT.md` for the gates it can measure: M2-G0 and G001 (one all-valid B6 unit, compute-only timer; informational N workers), M2-B11, M2-B12, M2-B16 (per-worker start with the snapshot, private and shared bytes), M2-B17 and T01 (store round trip, hash compared), M2-B18 (trade-to-grid, truth checked against the generator reference totals) and the determinism, equivalence, cache, memory, scaling and kill rows (D, E, C, R, S, K: a run at the requested workers, batch size, order, path, cache, mutation and fault, returning the per-unit and whole-run hashes and the store content hash). Unknown request fields, an unknown gate, fault or mutation kind, a mutation kind that does not apply to the gate (the M1 kinds `input` and `bound` apply to M1 gates only) and a gate that is not bound in this build (the rate and read gates M2-B1 to B10, B13 to B15r, P1-T1 and the M1 gate names, which the story benches measure) are errors: exit 2, `errors` named, `results` and hashes null, `partial_output` false. Worker count and timings appear only in the response fields the contract assigns them, never in `results` or `result_sha256`. Response extensions (additive): `timings_read_ns`, `timings_start_ns`, `store_private_bytes_per_worker`.

## Determinism rules
- Workers return (unit key, result bytes); the parent orders by unit key (never completion order) and hashes `unit key LF unit sha256 LF` in key order (`result_sha256`). Within a unit contracts are sorted by contract id.
- Worker count, worker ids, timings, counters and the clamp appear only in the run log, never in results or output files.
- Workers are spawned with `PYTHONHASHSEED=0`; no result depends on unsorted set or dict iteration (the Tester shuffles contract, unit and chunk order). Each worker sets its own process-global switches (python-flint threads = 1). Same interpreter and library versions in every worker, verified at start.
- Results at 1, 2, 4 and N workers, across batch sizes and unit orderings, are identical result bytes; the single-process run is the reference.
