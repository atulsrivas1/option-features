# 2026-10-30: M3a S02 history store and read forms, Developer choices

mock-data qualification only: passed on independently authored synthetic fixtures and synthetic workloads, Windows x64, CPython 3.12

Status: Developer choice (S02), for code and architecture review. R-43, R-48, R-51, R-52, R-79, R-89, R-110 to R-114, R-153, R-159, R-160, the IO contract section 4 view-read list (PR 112) and owner decisions 4 and 5 settle the rules. They leave the following open.

1. Where the record `delta_convention` lives (R-160 says a history record may carry the field; the M2 line has none). The store keeps it on the record as given (None, "spot" or "forward"; any other value is ValueError at append, since R-160 adds no append code). The canonical line carries `"delta_convention":"<value>"` after `complete` only when the field was given. Every M2 record has no field, so M2 lines, content hashes, dumps and snapshots are byte-identical (checked: m2 suite 963 tests, plus a 40-seed random M2 store digest of dump, snapshot, binary snapshot and reload, equal on origin/main and this branch). The binary snapshot table gets the keys `series_k` and `conv` only when used. Reason: the S10 series builder must write `skew25_fwd` records with "forward", and the round trip (M3A-B7) must keep it, or a forward read after a reload would be `convention_mismatch` (row M3A-H-069 rule).
2. `add_series(series_id, k)` (R-114) keys k by series id, so it covers every metric and window of that id. k > 60 is allowed only when the metric part of the id is an M3a metric (`atm_iv`, `atm_iv_close`, `iv30`, `iv30_close`, `skew25`, `skew25_fwd`, `term_30_91`) or a skew-type `<metric>_fwd` (R-159). Every other series keeps 1..60 (R-52). The constructor cap stays `MAX_K = 60`. Lowering k evicts the oldest records at once. Text has no k, so `load` and `from_snapshot` take `series_k={series_id: k}`. The binary snapshot restores it from its table.
3. View-read position 5 with a bad request `delta_convention` is settled by R-190 (Architect, 2026-10-30): on a skew-type series, a non-string, any string other than "spot" and "forward", and a supplied None are all `malformed_type` at position 5. "Not supplied" means "spot". `convention_not_allowed` belongs to request position 13 only. Convention-free metrics (R-159) skip position 5. The records checked are the selected ones (those the read uses).
4. `min_sessions` and `max_sessions` must be ints >= 1 (row M3A-H-014: 0 is `malformed_type`; bool is not an int). There is no upper bound on `max_sessions`, because retention bounds the read. `x` follows R-190 item 3: one rule shared with the request list, by calling `m3a_validate.validate_view_read`. That rule accepts a non-bool int, a Fraction, or integer / "a/b" text; float, Decimal, bool and other text are `malformed_type` at position 4. An unhashable series_id, metric or window_s is `malformed_type`, so the read never raises.
5. Read record: `HistoryRead(status, reason, code, value)`. On unavailable, `value` keeps `n` with `values` and `sessions` None (rows M3A-H-008, 024, 039). `values` and `sessions` are tuples, ascending by session.
6. Performance (owner main goal; M3A-B5 read share per R-193, B8). A read never builds a `HistoryView`, sorted copy or merged array, and keeps no per-call memo (R-193: derived read state is dropped per call). Each M3a ring has a store layout, `flowstore._Cols`, kept in step at append, seal and eviction. It is built once on the first read of a loaded or attached ring, and `build_m3a_layout()` builds it eagerly. The layout holds session-ordered columns: ids, totals, complete flags, grid lengths and conventions. A minute series also has ONE contiguous int64 block of k x stride values (stride = the longest calendar session), and a full dense grid without zeros lives there: the record's `vals` is a memoryview of its row and its `idx` is the shared full index, so there is no second copy. Rows are circular, so the minute column is one strided slice rotated by `head`. An evicted record gets a private copy of its row before the row is reused. Other grids (with zeros, beyond int64, or longer than the stride) keep their own arrays and are read record by record, with the same values. Cost: the int64 block is twice the narrowed 4-byte arrays, so the B6 store is about 235 MiB private bytes, inside 768 MiB. An M3a ring whose records hold block memoryviews cannot be pickled; nothing pickles a store today.
