# 2026-10-30: M3a S02 history store and read forms, Developer choices

mock-data qualification only: passed on independently authored synthetic fixtures and synthetic workloads, Windows x64, CPython 3.12

Status: Developer choice (S02), for code and architecture review. R-43, R-48, R-51, R-52, R-79, R-89, R-110 to R-114, R-153, R-159, R-160, the IO contract section 4 view-read list (PR 112) and owner decisions 4 and 5 settle the rules. They leave the following open.

1. Where the record `delta_convention` lives (R-160 says a history record may carry the field; the M2 line has none). The store keeps it on the record as given (None, "spot" or "forward"; any other value is ValueError at append, since R-160 adds no append code). The canonical line carries `"delta_convention":"<value>"` after `complete` only when the field was given. Every M2 record has no field, so M2 lines, content hashes, dumps and snapshots are byte-identical (checked: m2 suite 963 tests, plus a 40-seed random M2 store digest of dump, snapshot, binary snapshot and reload, equal on origin/main and this branch). The binary snapshot table gets the keys `series_k` and `conv` only when used. Reason: the S10 series builder must write `skew25_fwd` records with "forward", and the round trip (M3A-B7) must keep it, or a forward read after a reload would be `convention_mismatch` (row M3A-H-069 rule).
2. `add_series(series_id, k)` (R-114) keys k by series id, so it covers every metric and window of that id. k > 60 is allowed only when the metric part of the id is an M3a metric (`atm_iv`, `atm_iv_close`, `iv30`, `iv30_close`, `skew25`, `skew25_fwd`, `term_30_91`) or a skew-type `<metric>_fwd` (R-159). Every other series keeps 1..60 (R-52). The constructor cap stays `MAX_K = 60`. Lowering k evicts the oldest records at once. Text has no k, so `load` and `from_snapshot` take `series_k={series_id: k}`. The binary snapshot restores it from its table.
3. View-read position 5 with a bad request `delta_convention` is settled by R-190 (Architect, 2026-10-30): on a skew-type series, a non-string, any string other than "spot" and "forward", and a supplied None are all `malformed_type` at position 5. "Not supplied" means "spot". `convention_not_allowed` belongs to request position 13 only. Convention-free metrics (R-159) skip position 5. The records checked are the selected ones (those the read uses).
4. `min_sessions` and `max_sessions` must be ints >= 1 (row M3A-H-014: 0 is `malformed_type`; bool is not an int). There is no upper bound on `max_sessions`, because retention bounds the read. `x` follows R-190 item 3: one rule shared with the request list, by calling `m3a_validate.validate_view_read`. That rule accepts a non-bool int, a Fraction, or integer / "a/b" text; float, Decimal, bool and other text are `malformed_type` at position 4. An unhashable series_id, metric or window_s is `malformed_type`, so the read never raises.
5. Read record: `HistoryRead(status, reason, code, value)`. On unavailable, `value` keeps `n` with `values` and `sessions` None (rows M3A-H-008, 024, 039). `values` and `sessions` are tuples, ascending by session.
6. Performance (owner main goal; M3A-B5 read share per R-193, B8). A read never builds a `HistoryView`, sorted copy or merged array, and keeps no per-call memo (R-193: derived read state is dropped per call). Each M3a ring has a store layout, `flowstore._Cols`, kept in step at append, seal and eviction. It is built once on the first read of a loaded or attached ring, and `build_m3a_layout()` builds it eagerly. The layout holds session-ordered columns: ids, totals, complete flags, grid lengths and conventions. A minute series also has ONE contiguous int64 block of k x stride values (stride = the longest calendar session), and a full dense grid without zeros lives there: the record's `vals` is a memoryview of its row and its `idx` is the shared full index, so there is no second copy. Rows are circular, so the minute column is one strided slice rotated by `head`. An evicted record gets a private copy of its row before the row is reused. Other grids (with zeros, beyond int64, or longer than the stride) keep their own arrays and are read record by record, with the same values. Cost: the int64 block is twice the narrowed 4-byte arrays, so the B6 store is about 235 MiB private bytes, inside 768 MiB. An M3a ring whose records hold block memoryviews cannot be pickled; nothing pickles a store today.
7. Tester round 2, F2 (correctness). The all-or-nothing check was bypassable: `array("q", grid)` fell back to `narrow()` on OverflowError, and `narrow()` returns an unchecked tuple for values beyond 64 bits, so grids such as `[1, 10**30, Fraction(1, 3)]` were stored. The scalar `total` had no type check on M3a series either. Rule now, M3a series only (metric in M3A_METRICS or `<metric>_fwd`): before any mutation, every grid value (dense, or the values of a sparse record) must be an exact `int` (`type(v) is int`: not bool, float, Decimal, Fraction, str, bytes, None, complex), and an explicit `total` must be an exact `int`; otherwise `TypeError`, the same family M2 `narrow` raises, and the store is unchanged. Ints beyond 64 bits stay valid (kept as a tuple, as before; test_m10). `total=None` still means "sum of the grid". M2 series run no new check, so M2 bytes, errors and digests are unchanged. `append_record` / `append_many` take prebuilt `GridRecord`s and are not part of this rule.
8. Tester round 2, B7 (performance floors). Profiling the 181,692-record B6 store showed three costs, none in the format: (a) the cyclic collector scanning the hundreds of thousands of objects a load, attach or dump creates or walks (attach 87k to 138k rec/s with the collector paused); (b) the text writer building every dense grid with a per-point Python loop even when the record has no zero point (now one `repr` of the value list with separators removed: identical bytes); (c) per-record parse work, unchanged. `dump`, `load` and the binary attach now pause the collector for their duration and restore the previous state in `finally` (`flowstore._nogc`); no result changes, only timing. Numbers (30 fresh-process repeats, p5 of the rate) are in the PR comment; the budget document is not edited.
9. Tester round 3 (D1 to D5), M3a series only; M2 behaviour, errors and bytes unchanged (M2 100-store digest identical to main). (D1, D3) `append` accepts a grid that is exactly a `list` or `tuple`; anything else (bytes, bytearray, memoryview, array, generator, range, str, dict, list subclass) is `TypeError`. The grid is read once into a private list; the exact-int check, the stored values and the default total (`sum`) all use that copy, so a shape-shifting iterable cannot pass the check and store something else, and a later caller mutation changes nothing. An explicit `total` must be an exact `int` (`type(t) is int`: bool, float, Decimal, Fraction, str, bytes, None-as-explicit-not-possible, complex, nan, inf, IntEnum, int subclasses and numpy integers are rejected). (D4) Order is the M2 order: the structural codes (`lane_mismatch`, `session_not_in_calendar`, `record_length_mismatch`, `non_monotone_grid`, `duplicate_session`, `out_of_order_append`) come first as M2StructuralError, then the type TypeError, then the store; nothing is mutated before the last check. (D2) `append_record` and `append_many` apply the same rule to the values (integer-typed array or memoryview as is; list or tuple copied once to a tuple and every element an exact int; anything else TypeError) and to `total`. `append_many` is all-or-nothing for any batch that touches an M3a series: on any error every touched ring is restored to its pre-batch records (a ring created by the batch is removed) and the layout is rebuilt on the next read; a batch with no M3a series keeps the M2 behaviour (records before the failing one stay). (D5) The dense-grid text fast path (`repr` of the value list) is used only when every value is an exact int; any other accepted value (Fraction, Decimal, IntEnum, bool in the beyond-64-bit tuple form) goes through the previous per-point `str` writer, so the bytes are identical to the old writer for every accepted input (test_D5).
10. Performance numbers (Windows x64, CPython 3.12; fresh process per repeat, B6 store of 181,692 records). 30 repeats before round 3 (p5 / p50 / min, records per second): text write 33,317 / 36,133 / 24,492 (floor 25,000); text read 62,177 / 66,465 / 61,904 (floor 50,000); mmap attach 138,122 / 149,539 / 133,296 (floor 50,000); binary write 68,814 / 76,229 / 52,962; append 53,209 / 57,422 / 51,991 (floor 25,000). A 12-repeat run after round 3 ran while other jobs loaded the machine (every row including append dropped, text write minimum 14,987, text read minimum 22,505), so it is not a clean read; its best repeats (text write 33,854, text read 63,824, attach 156,581, append 52,760) match the clean run. The floors hold with 20 percent margin at p5 on the clean run; an individual repeat under load can fall below them. B17 (M2 text load of 200,125 records, 10 alternating main/head fresh-process reps on a loaded machine): best 52,034 (main) against 50,760 (head), medians about 36k against 42k; no slowdown found (the load path only gained the collector pause). B5: the scalar read on a convention-free metric no longer slices the convention column (about 1 us of 9.5 us per call).
