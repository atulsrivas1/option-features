# M3a S01 decision: place of `frame` in the result envelope, and unavailable labels

mock-data qualification only: passed on independently authored synthetic fixtures and synthetic workloads, Windows x64, CPython 3.12

Author: Developer (S01), 2026-10-30. Status: Developer choice inside the rulings; PO and Architect review at PR.

## Gap
IO contract section 3 lists the envelope keys (without `frame`); section 8.1 (R-108, R-141) declares the M3A-0 `frame`
object but no ruling places it in the canonical key order or says whether it appears on other outputs.

## Choice
1. `frame` is emitted directly after `value`, and only when set (M3A-0). Every other output keeps exactly the section 3
   key list, so no non-frame result byte depends on this choice. The M3a hash is new either way (R-64: no M1 or M2 byte
   changes).
2. An `unavailable` or `invalid_input` result carries `labels` = [] (R-105) even when a frame shows per-item values.
3. Nested dicts are emitted in producer insertion order (as M2 `canonical_line`); no sort at serialization, so the
   envelope overhead stays minimal (B4).
4. `params_echo` fills only the defaults the rulings state (mode, lane, stale_limit_ns, iv_form, delta_convention,
   delta_target, min_sessions, max_sessions, prior_sessions). `min_strikes`, `min_coverage`, `direction` and thresholds
   have per-output defaults owned by their stories and are echoed as given.

## Consequence
If the Architect prefers another position for `frame`, only `_wire` in `m3a_common.py` and one test change.
