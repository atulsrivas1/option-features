# M3a capability matrix (volatility surface, term structure, skew)

mock-data qualification only: passed on independently authored synthetic fixtures and synthetic workloads, Windows x64, CPython 3.12

Author: Architect, 2026-10-30. Status: DRAFT for PO decision and independent review; nothing here is ruled. Every PROPOSED item points to M3A_RULING_LIST.md (one batch, RECOMMENDED rulings, so the PO can rule everything in one pass before any fixture author starts). Companions: M3A_GATE_BUDGETS.md, M3A_FIXTURE_REQUIREMENTS.md, M3A_RULING_LIST.md, M3A_IO_CONTRACT.md. Format and rules baseline: docs/m2/* (matrix, budgets, fixtures, I/O contract, store API), docs/M1_CLOSE.md.

Sources of truth: design text volatility-radar.md (V rows, sections 2.3 to 2.10, 14), option-contracts.md (gates), audits/workers-vs-conditions.md (audit only), PO release plan V3 (M3 row), docs/FEATURE_STATUS.md (rows), docs/FLOW_NAMING_MAP.md (vocabulary), docs/m2/M2_STORE_API.md (history store).

Owner main goal: performance. Every M3a output is a pure, batched function over ONE chain at ONE cutoff plus read-only history views; contract IVs are solved once (M1 `IVChain`, certified solver unchanged) and reused by every output; history is read through the M2 store; the opt-in, default single-process runner (tools/m1_runner) supplies the cores; no result byte depends on worker count. All features first on synthetic data; adapter work only in RQ.

## 2. Legend and assumptions
Client = could run on a bring-your-own-key host if a provider supplies the data; Server = needs a full chain or history a single key will not supply; kernels are Either (pure, D4). Availability: FULL, DEGRADED, UNAVAILABLE (reason from the closed set, section 5). No silent fallback between sources; values from different sources are never merged. Data per the project data-sources assumption: mock/synthetic chains, daily totals and calendars generated by the Tester; vendor-style, FMP and public columns are shape only ("applies at RQ"). IV is modeled; every output is labelled "modeled" and carries American-style labels (M1: exact-model, approximate, american_itm).

## 5. Closed reason set and status
Statuses: available, unavailable (reason), invalid_input (structural code). The M3a reason set is closed; a new reason needs a PO ruling. Existing vocabulary is reused (no new synonyms where one exists):
| Reason | Origin | Meaning |
|---|---|---|
| no_atm_strike | M1 | no strike eligible for both rights near the forward |
| no_bracketing_expiry | M1 | a tenor or the second expiry has no bracketing or no second eligible expiry; no extrapolation |
| insufficient_history | M2 | fewer than the minimum complete prior sessions, including none stored (design "new") |
| insufficient_window | M2 | V3 before the first usable grid minute of the session |
| session_not_complete | M2 | end-of-day form before the session is sealed |
| zero_denominator | M2 | a ratio or percent-change denominator is 0 |
| no_delta_bracket | new | the 25-delta target is not bracketed by two eligible strikes of that right; no extrapolation |
| low_surface_coverage | new | the expiry lacks the minimum eligible strikes or coverage (R-20) |
| no_prior_reading | new | a change or sign change was asked and no prior reading exists (R-40) |
| zero_range_history | new (design VR P3) | the history has zero range, so a percentile is undefined |
Per-contract M1 reasons (no_quote, excluded_condition, invalid_quote, crossed_market, locked_market, stale_quote, american_itm, style_unknown) are not surface reasons: they exclude a contract and appear in `coverage` counts. Structural codes and the single precedence list are in M3A_IO_CONTRACT.md. Fixtures assert reason and status.

## 6. Dependencies on M1 and M2 modules (reused, not changed)
- `chainiv.IVChain` (contract_iv, atm_iv_all, iv_30d): the only source of IV; solver, stage filters and labels unchanged; each contract solved at most once per chain and cutoff.
- Greeks (R25 `evaluate` delta, modeled): the delta used to place the 25-delta point (R-04, R-05).
- M2 store (`flowstore` HistoryStore, views, canonical dump and load, mmap snapshot) and ranking (`flowrank` upper_share, rank_le, K and minimum rules, M2 Q2 and Q3): reused for V1, V3, V9; M2 closed sets, `Result`, canonical serialization and structural precedence rules are the baseline.
- Runner (tools/m1_runner): opt-in, default single-process; unit = underlying x session x cutoff; history views passed read-only.
